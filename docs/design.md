- 대리점별 월 장려금이 200만원 이하면 영업지원팀 전결, 초과하면 영업임원 승인이다. 동일 관련자는 지급 전 합산하며, 두 경로 모두 사람이 결정한다. [전결 규정](../01_참가자_배포용/04_원본데이터/00_common/approval_authority_policy.md)
- 대표자명·주소·등록 정산계좌 중 두 가지 이상이 일치하면 직접 연결한다. 직접 연결을 따라 이어지는 모든 대리점이 같은 그룹이다. 매출채권 회수에 쓰인 실제 입금계좌도 별도로 대조한다. [데이터 사전](../01_참가자_배포용/04_원본데이터/00_common/data_dictionary.md)

## 교육용 업무 가정

영업지원이 정산 자료를 취합하고 관계·한도를 검토한다. 필요한 사람의 승인 후 회계·자금이 지급·대사하고 영업지원이 소명 기록을 보관한다. 승인·소명 대기가 이어지면 후속 확인 의무가 남는다. 등록정보나 회수계좌의 공유는 소명을 검토할 정황이며 부정 확정의 근거로 사용하지 않는다. [W07 업무 설명](../01_참가자_배포용/세계관_BPMN/W07.html)

## 이번 구현의 설계 가정

1. 한도 적용월은 정산건의 **귀속월 `period_ym`**이다. 다음 달에 지급하더라도 그 금액은 원래 귀속월의 누계에 남는다.
2. **같은 그룹·같은 월의 기지급, 승인 후 미집행, 이번 심사 대상 금액을 합산**한다. 기지급·미집행 승인분은 결재 화면에서 기존 금액으로, 이번에 새로 승인받을 금액은 별도로 표시한다. 한도는 둘을 포함한 총액으로 결정한다.
3. 위 세 범주의 **`rebate_id` 합집합**에 대해 원 단위 금액을 건당 한 번만 더한다. **반려·취소 건은 제외**한다. 반려 후 보완·재접수하면 같은 ID의 새 유효 버전만 이번 심사 대상에 들어간다. 지급 보류 중인 유효 승인 금액도 다음 결재의 누계에 남긴다.
4. **관련자 그룹을 기준으로 결재안을 만들고 승인 후 대리점별 지급지시를 만든다.** 결재 명세에는 신규 승인 대상과 누계 참조 건의 역할을 구분한다. 지급지시는 신규 승인 대상의 대리점·정산건별로 만들며 동일 정산건에는 유효 지시를 하나만 둔다.
5. 해당 월의 적격 정산건을 함께 접수한다. 미지급이라는 원본 표기만으로 승인 또는 기지급 처리하지 않는다. 적격 정보가 충돌하거나 같은 ID에 다른 금액이 들어오면 원본 행을 보존하고 확인 작업을 연다. 그룹은 전체 마스터에서 계산하고 금액은 유효한 지급 대상만 더한다.
6. 직접 연결은 비어 있지 않은 등록 키만 비교한다. 이름·주소는 앞뒤 및 반복 공백을 정리하고 주소 상세는 보존한다. 계좌는 은행명과 구분기호를 정리한 번호를 함께 비교한다. `NONE`은 결측이다. 상호·사업자번호·회수계좌·AI 유사도는 일치 키 수에 더하지 않는다. 직접 연결이 없는 대리점은 단독 그룹이다.
7. 소명이 타당해도 등록 키에 따른 합산 규칙은 유지한다. 확인된 오류는 증빙과 적용일을 붙여 새 마스터 버전으로 정정한다. 담당자가 지급 판단에 필수라고 표시한 미해소 소명은 보완 대기로 보내고, 다른 그룹은 계속 처리한다.
8. 같은 그룹·월에는 심사 중인 결재안을 하나만 둔다. 상신·승인·지급지시 전송 시 최신 근거를 확인하고, 결재 버전과 적용 건 목록을 한 트랜잭션으로 검증·기록한다. 동시 접수로 심사 대상이 달라지면 새 합계를 제시해 다시 결정받는다. 과거 결재 버전으로 지급을 전송할 수 없다.

## 데이터 연결과 이력

| 업무 객체 | 연결 기준과 보존할 정보 |
|---|---|
| 대리점 | `agency_id`가 정산건·회수 이력의 공통 키다. 원본 등록 버전과 정정 버전별 적용일·세 키를 보존한다. 지급 수취계좌 확인 기록에는 별도 증빙과 버전을 둔다. |
| 정산건 | `rebate_id`가 한 지급 의무를 식별한다. 대리점 하나, 귀속월 하나, 원화 금액과 연결된다. 원본 승인상태·승인자·지급일은 앱의 결재·은행 처리 기록과 구분해 보존한다. |
| 관련자 그룹 | `group_version_id`에 구성원, 비교한 마스터 버전, 직접 연결 대리점 쌍과 일치 키를 보관한다. 단독 대리점도 구성원 1명의 그룹으로 표현한다. 결재 버전은 당시 그룹 버전을 참조한다. |
| 소명건 | `case_id`로 요건·대리점·관련 정산건 또는 결재 버전을 연결한다. 요청자·담당자·기한·회신·증빙·판단을 남긴다. 요청 → 회신 검토 → 해소 또는 추가 요청으로 진행한다. |
| 승인건 | `approval_id`와 버전으로 그룹 버전·귀속월을 연결한다. 명세에 정산건 ID별 금액·포함 사유, 합계·권한자·결정자·사유·시각을 고정한다. 재상신은 이전 버전을 참조한다. |
| 지급지시 | `instruction_id`마다 승인 버전의 신규 명세 하나, 대리점, 정산건, 지급액, 확인된 수취계좌 버전을 참조한다. 전송 시도와 재시도는 같은 지급 의무 아래 연결한다. |
| 은행 회신 | `reply_id`와 지급 시도 참조값으로 해당 지시를 식별한다. 모의 입력 여부, 은행 처리결과·금액·수취계좌·처리시각을 보존한다. 중복 회신이나 연결되지 않은 회신도 추적할 수 있게 한다. |
| 변경 이력 | `change_id`에 변경자·사유·기록시각·적용일·변경 전후 버전과 근거를 남긴다. 영향받은 그룹·정산건·승인건·지급지시 및 후속 검토를 연결해 정산건에서 원인을 역추적한다. |

## 상태 전환

승인 상태는 그룹 결재 버전에, 지급 상태는 개별 정산건의 지급 의무에 속한다. 같은 승인건 안에서도 각 지급건의 결과가 다를 수 있다.

| 승인 상태 | 사건·조건 | 다음 승인 상태와 담당자 |
|---|---|---|
| 작성 중 | 필수 정보 부족 / 근거와 누계 확인 완료 | 보완 대기(영업지원) / 승인 대기(규정상 권한자) |
| 승인 대기 | 권한자가 승인 / 보완 요청 / 반려 | 승인 / 보완 대기 / 반려. 결정 사유를 보존하고 승인된 신규 명세만 지급 준비로 넘긴다. 보완 요청·반려는 이번 요청분에 적용하고, 누계 참조용 기지급·기승인 건의 결정은 유지한다. |
| 보완 대기·반려 | 영업지원이 증빙·금액을 보완해 재상신 | 새 버전 승인 대기. 변경 전 결정은 이력에 남긴다. |
| 작성 중·보완 대기·승인 대기 | 영업지원이 집행 전 요청 철회 | 취소. 이후 심사에서 제외한다. |
| 승인 | 정정이 그룹·월 누계·승인 근거에 영향 | 재검토. 기존 승인 시점의 기록은 보존하고, 미집행 명세에 대한 효력을 보류한다. |
| 재검토 | 영업지원이 변경 전후를 비교 | 근거·권한·금액이 달라지면 새 버전 승인 대기. 영향 없음이 확인되면 기존 승인 유지 사유를 기록하고 보류를 해제한다. |

| 지급 상태 | 사건·조건 | 다음 지급 상태와 처리 |
|---|---|---|
| 지시 전 | 사람의 승인 | 개별 지시를 생성한다. 수취계좌 미확인은 지급 보류, 확인 완료는 전송 준비로 간다. |
| 전송 준비 | 유효 승인·금액·수취계좌 재확인 후 회계가 전송 | 회신 대기. 전송 시도 ID를 먼저 기록하고 모의 은행에 전달한다. |
| 지시 전·전송 준비 | 미집행 건에 영향을 주는 정정 또는 필수 증빙 부족 | 지급 보류. 회계 전송 목록에서 제외하고 재검토 또는 증빙 확인 작업을 생성한다. |
| 지급 보류 | 필요한 승인·계좌 확인 완료 | 유효 승인 명세로 전송 준비. 이전 버전의 미전송 지시는 대체 이력에 남긴다. |
| 회신 대기 | 성공 회신이 지시 ID·금액·수취계좌와 일치 | 대사 완료. 중복 회신은 기존 처리 결과를 반환한다. |
| 회신 대기 | 은행이 실패 확정 / 회신 미도착·정보 불일치 | 지급 실패 / 대사 확인 중. 회신 지연·불일치는 기존 시도 결과를 조회한다. |
| 대사 확인 중 | 일치하는 성공 확인 / 미지급 실패 확정 | 대사 완료 / 지급 실패. 결과가 불명확하면 확인 작업을 유지한다. |
| 지급 실패 | 회계가 실패 원인·미지급 여부를 확인하고 재처리 | 승인·계좌가 유효하면 전송 준비로 복귀해 새 시도 ID를 발급한다. 정정이 필요하면 지급 보류로 간다. |

**승인 후 정정의 적용 범위.** 적용일 기준 변경 전후 그룹의 구성원을 모두 찾아 영향받는 월의 기존 누계와 심사 대상을 재계산한다. 병합·분리로 승인권자가 바뀌면 해당 미집행 건을 새 권한자에게 상신한다. 지급 수취계좌만 달라지면 해당 지시를 보류하고 회계가 증빙을 재확인한다. 전송한 지시는 은행 결과를 먼저 대사하며 중복 전송을 막는다. 기지급분의 당시 승인·지급 기록과 당시 누계는 보존하고 사후 검토를 연결한다. 새 결재의 누계에는 정정 적용 범위에 속하는 기지급 건을 변경된 그룹에 건당 한 번 산입한다. 정정 적용일을 알 수 없으면 영업지원에 확인을 요청한다.

## 원본에 없는 정보와 보완 방법

| 정보 공백 | 로컬 앱에서 보완하는 방법 |
|---|---|
| 승인 당시 마스터와 변경·소명 증빙 | 최초 원본을 기준 버전으로 보존한다. 이후 입력은 정정 적용일·확인자·증빙을 기록한다. 과거 시점의 자료가 없으면 당시 상태를 미확인으로 표시한다. |
| 그룹별 결재서·상세 결정 이력 | 새 결재부터 근거와 누계를 저장한다. 과거 원장에 개인별 승인만 있으면 별도 임원 결재 유무는 확인 요청 대상으로 둔다. |
| 지급 수취계좌·은행 응답·지급 실패 사유 | 회계가 별도 수취계좌 증빙을 확인한다. 시연 입력은 모의로 표시한다. 회수계좌를 지급 지시에 복사하지 않는다. 은행 응답이 없으면 결과를 대기한다. |
| 원본의 승인·지급 혼합 표기 | `승인`과 지급일이 있으면 원장상 기지급으로 누계에만 반영한다. 은행 대사 여부는 미확인이다. `반려`는 제외하고 `미지급`·승인자 `NONE`은 접수 후 심사 대상으로 둔다. 과거 은행 회신이나 반려 사유를 생성하지 않는다. |

## 시연 사용자와 처리 기록

현재 로컬 앱의 시연 사용자는 영업지원 담당자, 영업지원 전결권자, 영업임원, 회계·자금 네 명이다. 화면에서 선택한 시연 사용자 ID를 서명된 세션에 저장한다. 서버는 결정 요청마다 세션 사용자의 역할과 해당 결재의 월 누계를 확인하고, 결정자와 역할을 기록한다. 시연 사용자 전환은 로컬에서 업무를 재현하기 위한 기능이다.

상신 시점과 사람의 결정 시점에 그룹 구성·등록정보, 일치한 키, 원본 정산건별 금액과 포함 사유, 연결된 소명 이력을 각각 저장한다. 필수 소명의 미해소 건은 승인을 막는다. 상신 이후 월 누계 또는 승인 근거가 달라지면 영업지원이 최신 명세로 재상신한다. 반려·보완 요청 후 재상신은 이전 결재를 참조하는 새 버전이다.

승인된 신규 명세의 지급지시는 최초 **지급 보류**로 생성한다. 회계·자금이 독립적으로 확인한 수취계좌·증빙 참조를 입력하면 모의 전송 준비로 이동한다. 확인은 개별 지시에만 적용한다. 같은 지시의 전송 시도와 은행 회신은 각각 고유 번호로 보존하며, 통신은 로컬 SQLite 안에서 모의 처리한다. 실패 확정 후 재시도는 기존 지시 아래 새 시도 번호로 기록한다.

## 로컬 기술 구성

**Python + Flask(서버 렌더링 HTML) + SQLite**로 네 화면을 하나의 로컬 프로세스에서 제공한다. 별도 DB 서비스나 프런트엔드 빌드 없이 결재 이력과 지급 상태를 디스크에 보존할 수 있다. Python의 CSV·SQLite 기능으로 원본을 읽고 같은 트랜잭션에서 업무 상태를 갱신한다. 개발 시에는 가상환경에 Flask를 설치하고 로컬 주소에서 실행한다.

AI 연결은 다음 지시에서 다룰 설계다. 이후 연결할 경우 서버에서 환경변수로 지정한 모델 API를 사용하고, 입력은 판정된 키 종류, 마스킹한 차이, 금액 등 설명에 필요한 정보로 제한한다. 현재 네 화면은 저장된 데이터, 고정 규칙, 사람의 결정으로 동작한다.
