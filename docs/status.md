# W07 개발 현황과 검증

## 현재 단계

월 정산 접수부터 소명, 그룹 결재, 지급지시·모의 은행 대사, 승인 후 등록정보 정정과 재검토까지 연결됐다. 관련자·소명 화면에서 영업지원이 등록정보를 정정하면 그룹 결재와 회계 대기열에 후속 작업이 표시된다. 기존 로컬 DB는 버전 4로 이관했다. 6월 접수 40건과 AI 초안 1건을 보존했고 모의 정정·지급은 별도 테스트 DB에서 처리했다. [D-001 등록정보 정정](http://127.0.0.1:5070/cases?month=2026-06&group=D-001#corrections)

### 로컬 실행

프로젝트 루트의 PowerShell에서 처음에는 `python -m venv .venv`와 `.\.venv\Scripts\python.exe -m pip install -r requirements.txt`를 실행한다. 이후에는 `.\.venv\Scripts\python.exe -B app.py`로 시작해 [월 정산 접수](http://127.0.0.1:5070/)를 연다. 기본 DB는 `instance/w07.sqlite3`이며 재실행하면 같은 파일을 사용한다. 6월 그룹은 [관련자·소명](http://127.0.0.1:5070/cases?month=2026-06&group=D-011), [그룹 결재](http://127.0.0.1:5070/approvals?month=2026-06&group=D-011), [지급지시·대사](http://127.0.0.1:5070/payments?month=2026-06&group=D-011)에서 이어서 처리한다.

### 실행 검증

- 2026-11-13 전체 테스트 **41개 통과**. 기존 24개와 정정 관련 17개를 함께 실행했다. 이 중 실모델 테스트 2개에서 총 5번 호출했다. 재현하려면 PowerShell에서 `$env:W07_TEST_LIVE_AI='1'`을 설정하고 `.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v`를 실행한다. [접수](../tests/test_intake.py) · [결재](../tests/test_approvals.py) · [지급·대사](../tests/test_payments.py) · [HTTP 검증](../tests/test_workflow_http.py)
- 6월 접수 전 적용 누계는 0원이고 예상액은 37,159,812원이다. 접수 후 실제 적용 누계는 예상액과 일치했다. 심사 대상 38개 그룹 중 임원 경로는 1그룹 3건이고, 팀 전결 경로는 37그룹 37건이다.
- 동시에 접수한 두 요청의 결과는 각각 신규 40건·기존 0건과 신규 0건·기존 40건이었다. HTTP 폼으로 접수 후 서버 프로세스를 종료하고 같은 DB로 재기동해 40개 정산 ID와 접수 시각이 그대로인 것을 확인했다. 재접수 결과도 신규 0건이었다.
- Chrome에서 월 전환, 대리점·정산 ID 검색, 승인 경로 필터, 페이지 이동, 직접 연결 근거와 D-024 회수계좌 차이, 접수·재접수 결과를 확인했다. 데스크톱 1440px 및 모바일 390px 너비로 점검했다.
- 경계값과 상태 조합은 원본 복사본의 추가 행으로 확인했다. 200만원은 팀 전결, 200만 1원은 임원 경로였고 반려·취소는 제외됐다. 같은 ID에 다른 금액이 오면 원금액을 보존한 채 해당 심사 건이 확인 대상으로 남았다. 잘못된 입력 행이 있으면 그 적재 회차의 새 행 전체가 롤백됐다.
- D-001의 실제 6월 988,932원은 전결권자가 승인했다. D-024에 필수 소명을 요청하자 상신이 보류됐고, 대리점 답변·증빙·해소 판단을 기록한 뒤 세 대리점 3,888,097원을 상신했다. 전결권자가 임원 역할을 폼에 임의로 기입한 요청은 서버가 HTTP 403으로 거절했다. 임원의 정상 승인 후에는 대리점별 3개 지시가 생성됐고, 모두 수취계좌 미확인으로 보류됐다.
- 금액 분리 검증에서는 이미 승인한 988,932원에 **시연용 신규 1,100,000원**을 추가했다. 월 누계 2,088,932원에 따라 임원에게 상신하고 이번 승인액인 1,100,000원에 대해서만 새 지시 하나를 생성했다. 반려·보완 요청 직후에는 지시 0건, 보완 후 재상신하면 이전 버전과 결정 사유가 보존됐다.
- 모의 회신은 금액 또는 은행·계좌가 다르면 대사 확인 중, 일치하는 실패는 지급 실패, 일치하는 성공은 대사 완료로 처리했다. 동시 전송·중복 회신에서 지시·시도·회신이 중복 생성되지 않았다. 별도 검증에서 3개 지시 중 계좌 증빙을 확인한 D-024만 대사를 완료하고 나머지 2건은 지급 보류를 유지했다.
- HTTP로 정상 건과 임원 그룹을 처리한 뒤 서버 프로세스를 종료·재기동했다. 결재 2건의 당시 근거·결정 기록, 지급지시 4건(대사 완료 1건·보류 3건), 회신 2건이 유지됐다. 소명·계좌 증빙과 은행 회신은 모두 검증용 모의 입력이다.

### AI 실제 호출과 결과 저장

- 실행 중인 앱에서도 브라우저의 ‘근거 요약 생성’을 눌러 **초안 #1**을 저장했다. 검토 대기로 남겨 원문을 열고 바로 수정·채택할 수 있다. 이 작업으로 생성된 결재·소명 요청·지급지시는 0건이다. [저장된 6월 그룹 요약](http://127.0.0.1:5070/cases?month=2026-06&group=D-011#ai-drafts)
- 2026-11-13에 Flask의 생성·채택 경로를 통해 기존 Codex CLI 로그인으로 `gpt-6.1-sol`을 실제 호출했다. 6월 D-011·D-024·D-037 그룹에서 질문은 D-024의 DP-00013·DP-00014 계좌 차이를 지목했고, 요약은 두 그룹 연결 근거와 시험용 대리점 답변을 반영했다. 결재안은 월 누계와 이번 상신액을 각각 3,888,097원으로 기재하고 영업임원 검토를 요청했다.
- 실제 모델 원문과 수정한 채택문을 각각 보존했다. 질문은 소명 요청 1건, 요약은 그룹 검토 메모, 결재안은 **승인 대기** 결재서 1건으로 연결됐다. 같은 질문을 두 번 채택해도 소명 요청은 1건이었다. DB를 다시 열어 문안을 확인했고 지급지시는 0건이었다.
- 위 시험의 대리점 답변·증빙·검토자 수정 문구는 시험 입력이다. 모델 응답은 실호출 결과다. 반면 기본 테스트의 역할·동시 채택·근거 변경·롤백·CLI 실패 분기는 모의 제공자 또는 모의 프로세스 응답으로 재현했다. [업무 저장 테스트](../tests/test_ai_drafts.py) · [제공자 오류 테스트](../tests/test_ai_provider.py)
- 실제 호출을 다시 검증하려면 로그인된 서버에서 PowerShell 환경변수 `$env:W07_TEST_LIVE_AI='1'`을 설정하고 `.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p test_ai_live.py -v`를 실행한다. 각 응답의 모델명과 호출 식별자가 출력된다. 다른 모델·로그인 환경과 모든 소명 문구의 정확도는 미검증이다. [실제 호출 테스트](../tests/test_ai_live.py)

### 승인 후 정정 검증

원본 CSV를 새 테스트 DB에 적재하고 2026년 6월분을 접수했다. D-001(RB-00006)을 팀 전결로 승인한 뒤 독립적인 시험 계좌 증빙을 등록해 전송 준비 상태로 만들었다. 6월 15일을 적용일로 대표자·주소를 D-011의 원본 값과 같게 정정했다.

| 확인 항목 | 관찰 결과 |
|---|---|
| 전후 그룹과 결재 한도 | 변경 전 D-001 단독 988,932원·팀 전결, D-011·D-024·D-037 합계 3,888,097원·영업임원. 변경 후 네 대리점의 월 누계 **4,877,029원**, 신규 승인액 **3,888,097원**, 기승인분 재승인액 **988,932원**. |
| 미전송 지시와 재상신 | 정정 직후 회계 전송 버튼이 사라졌고 서버도 직접 전송 요청을 차단했다. 서버 재시작 후에도 보류와 정정 이력이 유지됐다. 팀 전결 요청은 HTTP 403이었다. 임원 재승인 후 D-001은 기존 지시 번호로 전송 준비에 복귀했고, 신규 3건만 추가돼 총 지시는 4건이었다. |
| 이미 전송한 지시 | 기존 시도 번호로 금액·계좌·처리결과를 대조했다. 불일치·미확인 중에는 재전송할 수 없었다. 일치 성공은 사후 검토, 일치 실패는 재승인 후 동일 지시의 새 시도로 이어졌다. 중복 회신을 반복해도 추가 지급은 없었다. |
| 지급 완료와 등록계좌 정정 | 완료 건의 지시·계좌·금액·시도·회신은 동일했고 회계의 사후 검토 결과만 추가됐다. 별도 등록계좌 정정 시험에서는 임원 재승인 뒤에도 기존 수취계좌로 전송할 수 없었다. 회계 재확인 뒤 이전·새 계좌와 증빙을 모두 조회했다. |
| 기존 승인과 AI 초안 | 최초 결재의 근거·결정, 실제 AI가 생성한 정정 전 요약 원문과 담당자 채택문을 보존했다. 해당 초안에 재검토가 표시됐고 새 결재에서 제외됐다. 실모델이 생성한 정정 후 결재안에 4,877,029원·3,888,097원·988,932원과 영업임원이 모두 포함됐다. 정정 도중 AI 응답이 도착하는 경합은 모의 제공자로 검증했다. |

적용일·소급·예약 정정과 그룹 분리, 구버전 입력 차단, 원장상 기지급 검토, 신규 승인액 0원인 재승인도 검증했다. 로컬 DB 이관 전후 대리점·정산·회수 이력·AI 초안 행의 해시가 같았다. SQLite 무결성 및 외래 키 검사와 네 업무 화면의 HTTP 응답을 확인했다. ## 다음 작업과 미확인 항목

- D-001의 대표자·주소 정정은 재승인 경로를 검증하기 위한 모의 입력이다. 실제 변경 여부·적용일은 대리점의 등록 변경 증빙으로 확인해야 한다.
- 정정 후 처음 적재되는 월의 신규 건은 유효한 등록정보로 최초 심사한다. 정정 당시 DB에 없던 과거 기승인·기지급 행이 뒤늦게 들어오는 경우에는 후속 작업을 자동 생성하지 않는다. 배포 원본 밖의 과거 장부를 추가할 때는 승인 당시 등록정보·지급 증빙을 확인해야 한다.
- 승인 당시 마스터와 소명 증빙, 별도 임원 결재서, 실제 지급 수취계좌와 은행 처리결과는 미확인이다. 과거 결재 누락이나 실제 송금 결과의 단정은 피한다. 처리 방법은 [설계](design.md)에 있다.
- 원본 계좌는 수취계좌 증빙으로 자동 전용하지 않는다. 운영 은행이나 외부 송금 API 연결은 없으며, 시연 사용자 전환은 사내 인증을 대체하지 않는다.
