# W07 개발 현황과 검증

## 현재 단계

월 정산 접수부터 소명, 그룹 결재, 지급지시·모의 은행 대사, 승인 후 정정과 재검토까지 연결됐다. 현재 작업 소스의 DB 형식은 버전 9다. 이전 DB를 열 때는 먼저 작업용 사본을 만든다. [실행 방법](submission.md)

별도 기본 업무 DB와 지급계획 DB에서 사용 설명의 네 역할별 안내, 다른 역할 설명 열람 시 세션 권한 유지, 담당자 전환 후 설명 탭과 귀속월·그룹 유지, 지급계획 안내의 조건부 표시를 확인했다.

### 최신 제출 ZIP 실행 검증

`김상혁_W07.zip`에는 앱 소스 13개, 테스트 15개, `docs/` 문서 9개와 `demo-data/`의 시연 DB 2개 등 총 166개 파일이 있다. 시연 DB는 지급계획 시작본과 최종 화면 열람본이다. 검증용 DB는 개발 PC에 별도 보관한다. 실제 AI 4종의 호출 ID와 담당자 채택·후속 작업은 [업무 흐름 실행 검증](e2e-verification.md)에 기록했다.

전체 테스트 77개가 통과했다. 실제 모델 호출에는 이 PC의 기존 로그인을 사용했다. 다른 실물 PC·다른 계정에서의 설치와 AI 인증은 미검증이며, 모든 은행 회신과 출금은 모의 기록이다.

### D-001 대사 완료 후 금액·수취계좌 불일치

6월 D-001의 RB-00006을 팀 전결하고 수취계좌 확인과 자금 배정 후 988,932원을 한 번 모의 지급했다. 정상 성공 회신 `S1`으로 대사를 완료한 뒤, 같은 전송 시도에 성공 회신을 추가했다. 직전 ZIP과 수정한 ZIP에서 별도 DB로 같은 절차를 실행했다.

| 늦게 들어온 성공 회신 | 수정 전 | 수정 후 |
|---|---|---|
| 988,931원, 원래 수취계좌 | 금액 불일치 기록, 회계 작업 0건 | 금액 불일치 회신이 회계 작업 1건에 연결됨 |
| 988,932원, 다른 수취계좌 | 계좌 불일치 기록, 회계 작업 0건 | 계좌 불일치 회신이 회계 작업 1건에 연결됨 |
| 두 회신 모두 | 증빙 제출 HTTP 400 | 두 회신이 같은 작업에 연결됨. 회계가 지급 증빙·판단 근거와 `S1`을 선택해 지급 완료를 확인함 |

재검토 중 서버가 재전송과 미지급 전환을 거절했다. 다른 역할의 확정은 HTTP 403, 빈 증빙·불일치 회신을 지급 근거로 선택한 요청은 HTTP 400이었다. 동일 회신·확정을 반복하고 서버를 재시작한 후에도 최초 성공 회신과 출금 근거 `S1`, 전송 시도 1건, **988,932원 출금 1건**이 유지됐다. 내용이 일치하는 성공 회신은 다른 번호로 들어와도 재검토 작업 0건이었다. 담당자가 이미 확인한 불일치의 단순 사본도 새 작업을 열지 않았고, 새로운 계좌 차이는 별도 재검토로 이어졌다.

버전 8에서 불일치가 기록만 된 테스트 DB의 사본도 버전 9로 열었다. 회신을 다시 입력할 필요 없이 기존 불일치에 회계 작업이 생겼고, 당시 지급·출금과 회신 원문은 보존됐다. [모의 출금 및 회계 확인 회귀 테스트](../tests/test_funding.py)

### 최초 상신 전 RAW-X 후보 비교

직전 제출 ZIP과 수정본을 각각 새 DB에서 실행했다. 2026년 7월에 RAW-X(D-011)와 RAW-Y(D-024·775,000원)를 접수한 뒤, 상신 전에 RAW-X의 대리점만 D-037로 바꾸고 아래 금액을 입력했다. 원인은 심사액에서 보류된 RAW-X의 원본 기여액을 0원으로 취급한 것이었다. 표의 값은 접수 화면, 결재 화면, AI에 전달해 저장한 근거에서 공통으로 확인한 결과다.

| RAW-X 원본 / 추가 입력 | 수정 전 후보 합계와 승인권자 | 수정 후 후보 합계와 승인권자 |
|---|---|---|
| 1,300,001원 / 1,150,000원 | 775,000~1,925,000원 · 영업지원팀 | **1,925,000~2,075,001원 · 확정 대기** |
| 1,225,000원 / 1,150,000원 | 775,000~1,925,000원 · 영업지원팀 | 1,925,000~2,000,000원 · 영업지원팀 |
| 1,300,001원 / 1,225,001원 | 775,000~2,000,001원 · 확정 대기 | 2,000,001~2,075,001원 · 영업임원 |

각 경우에 두 번 재접수하고 서버 프로세스를 재시작한 뒤에도 정산 ID 2개, 미해결 입력 1개였다. 상신은 HTTP 400, 지급지시와 전송 시도는 각각 0건이었다. AI에는 현재 반영액 775,000원과 후보 범위를 구분해 전달하고, 미확정 월 누계와 신규 승인 요청액은 비워 둔다. 첫 사례에서 영업지원이 D-011 원본을 확정하자 월 누계와 신규 승인 요청액이 모두 2,075,001원인 영업임원 결재 1건이 생성됐다. 팀 결재 시도는 HTTP 403이었다. ### 같은 정산 ID에서 대리점과 금액이 바뀐 경우

수정 전 버전 7과 현재 버전 8을 각각 새 지급계획 DB에서 실행했다. 2026년 7월 TH-X(D-011·1,150,000원)와 TH-Y(D-024·775,000원)를 합계 1,925,000원으로 팀 전결하고, 두 지시의 계좌를 확인한 뒤 전액 배정했다. 입력 자료 사본에 TH-X의 대리점과 금액만 D-037·1,350,000원으로 바꾼 행을 추가해 두 번 재접수했다. 서버 프로세스를 재시작한 뒤 전송을 직접 요청하고 DB에서 지시별 지급 시도 수를 확인했다.

| 직접 전송한 지시 | 수정 전 | 수정 후 |
|---|---|---|
| 7월 TH-X | HTTP 400 · 시도 0건 | HTTP 400 · 시도 0건 |
| 7월 TH-Y | **HTTP 303 · 775,000원 전송 1건** | **HTTP 400 · 시도 0건** |
| 같은 그룹 8월 50,019원 / 다른 그룹 7월 32,123원 | 각각 한 번 모의 대사 완료 | 각각 한 번 모의 대사 완료 |

원인은 월 누계 보류 검사에서 **원본과 대리점 ID가 같은 입력만** 금액 충돌로 읽던 조건이었다. 수정 후 TH-X는 정산 1건·미확정 추가 입력 1건이다. 기존 누계 **1,925,000원**과 D-037 후보를 선택했을 때의 **2,125,000원**을 보여주고, 승인권자를 ‘확정 대기’로 표시했다. 반복 접수와 재시작으로 새 입력이 채택되거나 정산건이 추가되지 않았다.

- **D-011 원래 입력 확정.** 기존 팀 결재와 배정으로 두 건을 지급했다. 별도 실행에서 TH-Y에 은행 상충 회신이 있으면 TH-X의 판정 이후에도 TH-Y의 재전송이 차단됐다.
- **D-037 추가 입력 확정.** 금액만 제출하거나 서로 다른 후보의 대리점·금액을 조합한 요청은 HTTP 400이었다. 영업지원이 D-037·1,350,000원과 판단 근거를 기록한 뒤 두 지시를 재상신했다. 팀 승인은 HTTP 403, 영업임원 재승인액은 **2,125,000원**, 신규 승인액은 **0원**이었다. TH-Y의 775,000원 배정은 유지됐다. TH-X는 전액 재배정 후에도 새 수취계좌 확인 전까지 전송되지 않았다. 이전 D-011용 계좌 확인 요청도 거절됐다. D-037 계좌 증빙을 확인한 후 기존 두 지시를 각각 한 번씩 모의 대사했다.
- **기존 기록.** 이미 완료된 TH-X에 변경 입력이 들어온 실행에서 D-011의 기지급 1,150,000원, 회신과 출금은 그대로였다. 버전 7 테스트 DB 사본을 버전 8로 열면 재접수 없이 기존 충돌을 찾아 두 지시를 보류했고, 기존 전송 시도의 대리점과 결재 이력을 보존했다. 동시 연결 후 SQLite 무결성·외래 키 검사도 통과했다. [회귀 테스트](../tests/test_agency_amount.py) · [판정과 보류 범위](design.md)
- **보류가 겹친 경우.** 별도 DB에서 TH-Y에도 금액 충돌을 만든 뒤 TH-X만 확정하고 서버를 재시작했다. 두 지시 모두 HTTP 400이었다. 두 충돌을 해소한 뒤에도 필수 소명이 남아 있는 동안 재상신이 차단됐고 지급 시도는 0건이었다. 소명, 영업임원 승인, 자금 재배정과 새 수취계좌 확인을 마친 뒤 두 지시가 합계 2,125,000원으로 모의 대사됐다.

**전체 테스트 73개 재실행 통과, 실패·건너뜀 0개.** 대리점·금액 충돌 회귀 테스트 3개를 포함해 `W07_TEST_LIVE_AI=1`로 실행했다. 두 확정 경로에서 TH-X 원본·충돌 입력·담당자 판정은 각각 1건으로 유지됐고, 모의 대사 후 두 테스트 DB의 무결성·외래 키 검사에서도 오류가 없었다. 배포 원본 107개와 기존 개발·시연 DB 7개를 포함해 화면 템플릿, 디자인, 기존 제출물 등 133개 파일의 SHA-256이 재검증 전후 일치했다.

### 회계가 확정한 은행 회신과 출금 근거

수정 전후에 독립된 지급계획 DB와 같은 입력을 사용했다. 6월 D-011 그룹 3,888,097원을 임원이 승인한 뒤 D-011의 RB-00054에 수취계좌 증빙과 **1,373,515원**을 배정했다. 기준 잔액은 **3,000,000원**이었다. 1차 실패 `F1` → 2차 성공 `S2` → 뒤늦은 1차 성공 `S1` 순서로 모의 은행 회신을 입력하고, 회계가 두 시도를 대조한 증빙과 함께 `S1`을 지급 근거로 확정했다.

| 확인한 기록 | 수정 전 | 수정 후 |
|---|---|---|
| 회계의 결정과 유효 출금 | 결정은 1차 `S1`, 출금은 2차 `S2`를 가리켰다. | 결정과 출금이 모두 1차 `S1`을 가리킨다. 출금 1건·1,373,515원, 잔액 1,626,485원이다. |
| 변경 경위 | 2차 출금 처리와 1차 회계 결정이 따로 남았다. | 지급지시·대사에서 `S2 → S1`, 확인자·증빙 사유·시각을 조회했다. 당시 2차 성공으로 차감한 처리 이력 1건과 은행 회신 3건은 원래 값 그대로였다. |
| 반복 제출 및 재시작 | 동일 요청이 거절됐고 재시작 후에도 출금 근거가 `S2`였다. | 같은 확정을 재시작 전후 반복해도 회계 결정과 근거 변경은 각각 1건이었다. 같은 화면에서 다른 성공 회신으로 바꿔 제출한 요청은 HTTP 400이었다. |

출금 반영 후 잔액 **1,626,485원**을 별도의 새 마감잔액으로 입력한 테스트에서도 최초 출금일·기준 잔액 번호가 유지돼 재차 차감되지 않았다. 버전 6 시연 DB 사본 6개로 이관을 검증했다. 미결 회신은 그대로 두고 기존 회계 결정을 현재 유효 출금에 반영했다. 취소한 출금은 다시 생성되지 않았고, 취소 후 별도 시도로 지급한 건은 그 시도의 성공 회신을 유지했다. [출금 회귀 테스트](../tests/test_funding.py) · [지급계획의 처리 규칙](payment-plan.md)

**전체 테스트 70개 통과, 실패·건너뜀 0개.** 기존 69개와 이번 회귀 테스트 1개를 별도 DB에서 `W07_TEST_LIVE_AI=1`로 실행했다. 배포 원본 107개, 기존 개발·시연 DB 7개와 기존 제출물의 파일 해시가 작업 전후 일치했다. 지급·출금은 모의 은행 대사이며 현재 수정본은 작업 소스에 반영했다.

### 금액·승인 표기가 함께 바뀐 입력의 지급 통제

기존 제출본과 수정한 작업 소스에 동일한 6월 원본 사본과 입력 순서를 적용했다. 각각의 독립 지급계획 DB에서 계좌 확인·전액 배정 후 실제 로컬 웹 서버에 직접 전송을 요청했다. 두 환경 모두 충돌 입력에는 금액 **2,188,932원**, 승인 상태 **승인**, 승인자 **영업임원**을 기재했다.

| 모의 입력과 확인할 지급지시 | 수정 전 | 수정 후 |

A-EXTRA의 100,000원 배정은 유지됐고, RB-00006만 새 금액으로 전액 배정하자 기존 두 지시가 각각 한 번씩 모의 대사됐다. 최초 결재서는 보존됐고 새 결재서에는 금액과 승인 판단 근거가 함께 남았다.

**다른 보류와 기존 DB.** D-024의 추가 입력이 잘못됐다고 확인한 실행에서는 최초 결재로 D-011이 정상 지급됐다. D-024 자신의 은행 회신 상충은 계속 재전송을 막았다. 기존 버전 5 테스트 DB 사본을 버전 6으로 열자 재접수 없이 미해소 혼합 입력을 찾아 두 지시를 보류했고, 이전에 확정한 단순 금액 판단과 배정액은 유지됐다. 재시작·동시 연결 후에도 SQLite 무결성 및 외래 키 검사를 통과했다. | 지급 완료와 등록계좌 정정 | 완료 건의 지시·계좌·금액·시도·회신은 동일했고 회계의 사후 검토 결과만 추가됐다. 별도 등록계좌 정정 시험에서는 임원 재승인 뒤에도 기존 수취계좌로 전송할 수 없었다. 회계 재확인 뒤 이전·새 계좌와 증빙을 모두 조회했다. |
| 기존 승인과 AI 초안 | 최초 결재의 근거·결정, 실제 AI가 생성한 정정 전 요약 원문과 담당자 채택문을 보존했다. 해당 초안에 재검토가 표시됐고 새 결재에서 제외됐다. 실모델이 생성한 정정 후 결재안에 4,877,029원·3,888,097원·988,932원과 영업임원이 모두 포함됐다. 정정 도중 AI 응답이 도착하는 경합은 모의 제공자로 검증했다. |

적용일·소급·예약 정정과 그룹 분리, 구버전 입력 차단, 원장상 기지급 검토, 신규 승인액 0원인 재승인도 검증했다. 로컬 DB 이관 전후 대리점·정산·회수 이력·AI 초안 행의 해시가 같았다. SQLite 무결성 및 외래 키 검사와 네 업무 화면의 HTTP 응답을 확인했다. ## 다음 작업과 미확인 항목

- D-001의 대표자·주소 정정은 재승인 경로를 검증하기 위한 모의 입력이다. 실제 변경 여부·적용일은 대리점의 등록 변경 증빙으로 확인해야 한다.
- 정정 후 처음 적재되는 월의 신규 건은 유효한 등록정보로 최초 심사한다. 정정 당시 DB에 없던 과거 기승인·기지급 행이 뒤늦게 들어오는 경우에는 후속 작업을 자동 생성하지 않는다. 배포 원본 밖의 과거 장부를 추가할 때는 승인 당시 등록정보·지급 증빙을 확인해야 한다.
- 승인 당시 마스터와 소명 증빙, 별도 임원 결재서, 실제 지급 수취계좌와 은행 처리결과는 미확인이다. 과거 결재 누락이나 실제 송금 결과의 단정은 피한다. 처리 방법은 [설계](design.md)에 있다.
- 원본 계좌는 수취계좌 증빙으로 자동 전용하지 않는다. 운영 은행이나 외부 송금 API 연결은 없으며, 시연 사용자 전환은 사내 인증을 대체하지 않는다.
